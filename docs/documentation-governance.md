# VCPDeck 文档管理与维护规范

> 状态：Current｜维护责任：项目维护者｜最后核验：2026-08-15｜适用版本：当前 `main`

本文是 VCPDeck 文档分类、权威关系、生命周期、维护责任、归档和清理规则的统一事实来源。它规定“文档应该写在哪里、何时更新、何时删除或归档”，不描述具体业务实现。

## 1. 目标

文档体系应保证：

- 当前事实、长期决策、实现设计、未来规划和历史材料彼此分离；
- 开发者和 AI 能快速找到本次任务必须遵守的约束；
- 已实现能力不被写成规划，尚未实现的规划不被写成现状；
- 代码变化时，对应文档可以在同一变更中同步；
- 一次性过程材料不会长期污染项目知识；
- 重要决策不会因清理旧材料而丢失。

## 2. 长期文档结构与职责

```text
README.md                         # 项目入口、当前能力、边界、快速开始
AGENTS.md                         # 编码代理必须遵守的强制规则
CONTRIBUTING.md                   # 开发、评审、测试和文档检查流程
CHANGELOG.md                      # 用户或运维可感知的版本变化

docs/
├── index.md                      # 长期文档导航
├── documentation-governance.md  # 本规范
├── architecture.md              # 当前系统结构和组件边界
├── tech-stack.md                # 当前技术选型、用途和约束
├── domain-model.md              # 当前实体、状态机和不变量
├── protocols.md                 # 当前 REST、Socket.IO、SSE 等协议语义
├── compatibility.md             # 当前组件和协议兼容策略
├── deployment.md                # 部署要求、配置和升级
├── operations.md                # 启停、巡检、备份、恢复和故障处理
├── security.md                  # 当前信任边界、安全模型和已知风险
├── testing.md                   # 测试层次、命令和发布门禁
├── roadmap.md                   # 尚未实现的方向和优先级候选
├── adr/                          # 长期架构决策及其演进历史
├── design/                       # 确需长期维护的复杂功能设计
└── archive/                      # 已失效但仍有历史价值的材料
```

### 2.1 根目录文档

| 文档 | 只负责什么 | 不应包含什么 |
| --- | --- | --- |
| `README.md` | 项目定位、当前能力、明确边界、快速开始、文档入口 | 完整架构细节、实施计划、详细运维手册、重复路线图 |
| `AGENTS.md` | AI/编码代理必须执行的项目规则 | 大段背景分析、一次性任务说明 |
| `CONTRIBUTING.md` | 开发和 PR 流程、最低检查项 | 完整架构说明、所有文档治理细节 |
| `CHANGELOG.md` | 用户、开发者或运维可感知的版本变化和迁移要求 | 开发过程、内部推理、未确认计划 |

### 2.2 Current 文档

下列文档描述当前 `main` 的事实：

- `architecture.md`
- `tech-stack.md`
- `domain-model.md`
- `protocols.md`
- `compatibility.md`
- `deployment.md`
- `operations.md`
- `security.md`
- `testing.md`

Current 文档应解释稳定的结构、语义和操作方法，不复制可以直接从类型或 schema 读取的大量字段。运行行为变化时，必须在同一变更中更新相应 Current 文档。

### 2.3 ADR

ADR 记录长期影响系统结构、数据、协议、安全、兼容或运维的决策，主要回答：

- 为什么必须决策；
- 最终选择什么；
- 放弃了哪些重要方案；
- 接受了哪些后果；
- 什么条件下重新评估。

Accepted ADR 不改写历史结论。决策变化时创建新 ADR，并将旧 ADR 标记为 `Superseded by ADR-NNNN`。具体模板、状态和索引见 [`adr/README.md`](./adr/README.md)。

### 2.4 长期专题设计

`docs/design/` 只保存需要持续维护的复杂功能设计。专题进入该目录应同时满足：

- 模块具有跨组件、复杂状态机或重要失败路径；
- 仅阅读代码难以理解完整行为；
- 后续维护者会持续使用；
- 文档有明确负责人并会随实现更新；
- 内容不是一次性文件清单或实施步骤。

专题设计说明“模块如何协作”，ADR 说明“为什么选择这条长期路线”，Current 文档说明“系统现在是什么样”。三者不能互相替代。

### 2.5 Roadmap

`roadmap.md` 只保存尚未实现的产品方向、可靠性事项和优先级候选。它不代表交付承诺，也不能作为当前能力依据。候选能力开始实施后，应先完成必要的需求、设计、安全、兼容和 ADR 评审。

### 2.6 Archive

`archive/` 保存已经失效、但仍具有明确历史价值的材料。归档材料不能作为当前实现依据；归档和删除标准见 [`archive/README.md`](./archive/README.md)。

## 3. 文档权威关系

不同资料回答不同问题，不能用单一排序替代判断。

### 3.1 当前运行事实

判断“系统现在实际如何运行”时，优先级为：

1. 当前代码和运行时行为；
2. `packages/shared/src/` 中的协议定义和解析器；
3. `packages/server/prisma/schema.prisma` 与有效数据库迁移；
4. 当前配置读取逻辑和构建/发布脚本；
5. Current 文档；
6. 长期专题设计；
7. Roadmap 和归档材料。

测试用于验证事实，但测试本身也可能过期；测试与实现冲突时必须调查，不能只凭测试名称作结论。

### 3.2 决策意图

判断“为什么这样设计、哪些边界是有意识选择”时，以仍然有效的 Accepted ADR 为权威。ADR 不覆盖代码事实；如果代码与 ADR 冲突，必须明确报告并由维护者判断：

- 实现偏离了决策，需要修复代码；或
- 决策已经改变，需要创建新 ADR 替代旧 ADR并同步实现。

禁止通过静默修改 ADR 或文档来掩盖冲突。

### 3.3 明确需求

维护者对当前任务的明确要求可以改变既有方向，但若它改变 Accepted ADR、数据权威、协议兼容、安全边界或部署模型，应先指出冲突并创建 Proposed ADR，经确认后再实施。

## 4. 文档状态

长期文档使用下列状态：

| 状态 | 含义 |
| --- | --- |
| `Current` | 描述当前代码，可作为维护依据 |
| `Design` | 已确认的长期设计，可能仍在演进，必须结合代码核验 |
| `Proposal` | 候选方案，尚未成为约束 |
| `Planning` | 路线图和优先级候选，不代表交付承诺 |
| `Archived` | 已失效，仅保留历史背景 |
| `Superseded` | 已被明确的新文档或 ADR 替代 |

ADR 额外使用 `Proposed`、`Accepted`、`Rejected`、`Deprecated` 和 `Superseded by ADR-NNNN`，以 ADR 目录规则为准。

除 README、导航、索引和 CHANGELOG 外，长期文档顶部应至少标明：

```text
状态｜维护责任｜最后核验日期｜适用版本或事实来源
```

状态只能表示文档用途，不能用 `Current` 把未实现设计包装成现状。

## 5. 内容应该写到哪里

| 变化或知识 | 维护位置 |
| --- | --- |
| 项目定位、当前能力、快速开始 | `README.md` |
| 当前组件、依赖方向、通信和部署关系 | `architecture.md` |
| 技术版本、用途、技术约束 | `tech-stack.md` |
| 实体、关系、状态机和不变量 | `domain-model.md` |
| REST、Socket.IO、SSE、错误、重连语义 | `protocols.md` |
| 组件版本、协议版本、升级与破坏性变化 | `compatibility.md` |
| 配置、目录、首次部署、升级和回滚 | `deployment.md` |
| 启停、巡检、备份恢复、容量和故障处理 | `operations.md` |
| 信任边界、凭据、授权、风险和事件响应 | `security.md` |
| 测试层次、命令、覆盖要求和发布门禁 | `testing.md` |
| 长期重大决策及其理由 | `adr/` |
| 需要持续维护的复杂模块设计 | `design/` |
| 尚未实现的方向和优先级 | `roadmap.md` |
| 用户或运维可感知的变化 | `CHANGELOG.md` |
| 已失效但仍有历史价值的材料 | `archive/` |

同一项变更可能需要更新多个位置。例如协议状态机变化通常同时涉及 Shared、`domain-model.md`、`protocols.md`、`compatibility.md`、测试和 CHANGELOG；如果改变了长期取舍，还必须新增 ADR。

## 6. 开发过程中的文档生命周期

### 6.1 开发前

1. 从 [`index.md`](./index.md) 找到相关 Current 文档；
2. 阅读相关 Accepted ADR 和长期专题设计；
3. 核对代码、Shared、Prisma 和配置事实；
4. 判断需求是否改变长期决策或安全/兼容边界；
5. 如有冲突或新的重大取舍，先提出 Proposed ADR，不直接编码。

### 6.2 开发中

- 设计与实现发生偏移时，先确认是实现调整还是长期决策变化；
- 不在 Current 文档中提前声明尚未完成的能力；
- 不把临时推理、调试记录、文件修改步骤写进长期文档；
- 新发现但不在本次范围内的事项进入 Issue 或 `roadmap.md`，不能伪装成已完成。

### 6.3 开发完成时

必须进行知识收敛：

1. 将新的长期取舍写入 ADR；
2. 将当前事实同步到对应 Current 文档；
3. 将复杂且需持续维护的内部设计更新到 `design/`；
4. 将未完成事项转入 Issue 或 `roadmap.md`；
5. 将用户或运维可感知变化写入 `CHANGELOG.md`；
6. 删除仅服务本次任务的过程材料；
7. 对确有历史价值但已失效的材料执行归档；
8. 检查文档链接、状态、日期及与代码的一致性。

## 7. 删除、归档与替代

### 7.1 应直接删除

以下内容在任务完成且有效知识已收敛后通常直接删除：

- 一次性实施步骤和文件修改清单；
- 调试过程、AI 推理和自审记录；
- 已解决问题的临时分析；
- 已由代码、测试和长期文档完整承接的重复说明；
- 没有独立历史价值的过时副本。

Git 历史已经保存被删除内容，不需要为了“以后也许有用”永久保留。

### 7.2 应归档

只有以下材料值得归档：

- 曾正式采用、后来被替代的重要设计；
- 被拒绝但将来可能重复讨论的重要方案；
- 重大迁移、事故或兼容演进背景；
- 对理解历史版本仍有独立价值的材料。

归档前必须把仍然有效的当前事实、决策和未完成事项分别迁移到 Current 文档、ADR 和 Roadmap/Issue。

### 7.3 不得删除的历史

- Accepted、Rejected 或已被替代的 ADR 不得静默删除；
- 已发布版本的 CHANGELOG 记录不得改写成新的历史；
- 安全事故、破坏性迁移等需要保留的正式记录不得仅因内容过时而删除。

## 8. AI 编码规则

AI 在处理代码或文档任务时必须：

1. 先读取 `AGENTS.md` 和相关 Current 文档；
2. 查找并遵守相关 Accepted ADR；
3. 以代码、Shared、Prisma 和配置读取逻辑核验当前事实；
4. 发现代码、ADR 和 Current 文档冲突时停止猜测并报告；
5. 需求改变现有 ADR 时，先说明影响并提出替代 ADR；
6. 不把 Roadmap、Proposal 或 Archived 内容写成现有能力；
7. 完成后同步受影响的长期文档和 CHANGELOG；
8. 清除不再需要的过程材料，避免它们被后续 AI 当作事实；
9. 在最终回复中说明更新了哪些文档以及仍存在的事实缺口。

仅让 AI “阅读整个 docs”不是合适做法。应根据任务范围读取文档中心、相关 Current 文档、相关 ADR 和必要的专题设计，减少过时或无关上下文干扰。

## 9. 维护责任与核验频率

- 修改运行行为的人负责同步相关文档；
- 模块负责人负责对应 Current/Design 文档；
- 架构维护者负责 ADR 状态和架构边界；
- 发布维护者负责 compatibility、deployment、operations 和 CHANGELOG；
- 安全相关变更由实现者和安全责任人共同核验；
- “最后核验”表示文档与代码完成过事实核对，不应只因格式修改而机械更新。

建议在以下时点执行文档核验：

- 合并行为、协议、数据或配置变更前；
- 发布候选生成前；
- 重大重构或迁移完成后；
- 发现文档与代码冲突时；
- 定期维护清理时。

## 10. PR 文档检查清单

```markdown
- [ ] 已确认本次变更影响哪些长期文档
- [ ] 实现与相关 Accepted ADR 一致
- [ ] 新的长期决策已创建或替代 ADR
- [ ] 当前事实已更新到对应 Current 文档
- [ ] 协议/状态变化已更新 domain-model、protocols 和 compatibility
- [ ] 数据、配置、部署或恢复变化已更新 deployment/operations
- [ ] 信任边界和敏感数据变化已更新 security
- [ ] 测试策略或门禁变化已更新 testing
- [ ] 用户或运维可感知变化已更新 CHANGELOG
- [ ] 未完成事项只进入 Roadmap 或 Issue
- [ ] 无长期价值的过程材料已删除
- [ ] 失效但有历史价值的材料已归档并标明替代文档
- [ ] 文档链接、状态、日期和事实一致性检查通过
```

## 11. 禁止事项

- 不把未来规划写进 Current 文档或 README 当前能力；
- 不把 ADR 写成详细实施计划；
- 不用专题设计代替协议、部署或运维文档；
- 不复制大量 DTO、schema 或源码，导致双份事实来源；
- 不保留多个互相冲突但都标为 Current 的文档；
- 不直接改写 Accepted ADR 的历史结论；
- 不因文档过时而跳过有效知识收敛；
- 不因“可能有用”而永久保存所有过程材料；
- 不让归档材料继续作为当前文档的唯一依据。
