## 3. A2A 取消

派发长任务 `task_e37369d1a9cb4a92`（要求每 10 秒输出一次、共 12 次），在 `/agent-tasks` 详情抽屉操作：

1. 点「取消任务」→ 进入确认态（出现「放弃」/「确认取消」），此时**未**发出 `CancelTask`；
2. 点「确认取消」→ 4 秒内 `GetTask` 返回 `TASK_STATE_CANCELED`；
3. 事件链尾记录 `#132 task.canceled [acp]`；
4. 抽屉刷新为「已取消」，取消按钮消失。

UI 与服务端走同一条 `CancelTask`，`vcpdeck tasks cancel` 是同一路径。

## 5. FRP 承载端口暴露

- 建映射：`POST /api/frp/mappings`（`localPort=3001` → `remotePort=17055`，测试 frps 端口池 `17001-17100`）；
- 可达：`GET http://127.0.0.1:17055/api/health` 返回 Client 侧服务响应 `{"ok":true}`；
- 删除：`DELETE /api/frp/mappings/<id>` 后该端口立即不可达；
- 删除最后一条映射后 `~/.vcpdeck/frp/frpc-combined.toml` 被写成空配置（无残留 proxy 块）。

失败可见性：`remotePort=39999` 越界返回 `400 FRP_PORT_OUT_OF_RANGE` 与「端口 39999 超出实例配置范围 17001-17100」，不再退化为笼统 `500 FRP 操作失败`。

probe 计数：frps 会保留已断开 frpc 的统计条目（`conf: null`、`lastCloseTime` 有值、端口已释放），`proxies.offline` 因此累加；判断实际隧道看 `online` 与数据库记录。

## 6. 线上自更新（prod，2026-10-20）

0.22.0 是首次删表升级，发布构件的 `preStart` 是 `prisma db push`（不带 `--accept-data-loss`），直接上传会在切换版本前失败并回滚。因此按「先迁库、再上传」执行：

1. 备份：`/opt/vcpdeck/launcher/server.db` → `server.db.bak-pre-0.22.0-20261020-231418`（31 MB）。
2. 取 0.22.0 的 schema（`packages/server/prisma/schema.prisma`，与打包进构件的是同一份），把 `generator output` 改到 `/tmp/vcpdeck-mig/generated` 以免覆盖运行中应用的 client，写入目标机。
3. 迁移：`node node_modules/prisma/build/index.js db push --accept-data-loss --schema=/tmp/vcpdeck-mig/schema.prisma --url=file:/opt/vcpdeck/launcher/server.db` → `Your database is now in sync`。
4. 校验：`sqlite_master` 共 38 张表，`RemoteDev*` 残留 0 张，`Task` / `TaskTurn` / `TaskAttempt` / `TaskEvent` / `TaskArtifact` 均在。
5. 上传：`vcpdeck release upload win-x64.zip linux-x64.zip --env prod --wait` → Server 0.22.0，11 台 Client 全部 done、0 失败。
6. 升级后：`/api/remote-dev/sessions` 返回 404（RDS 端点已消失）、`/api/health` 200；临时目录 `/tmp/vcpdeck-mig` 已清理。

注意点：Prisma 7 CLI 已移除 `--skip-generate`，`db push` 只有 `--config/--schema/--url/--accept-data-loss/--force-reset`；远程执行时 `node` 不在 root 的 PATH 里，必须用绝对路径（本机为 `/opt/vcpdeck/client/node/current/bin/node`）。

## 8. 跨机 A→B 委托（prod，2026-10-21）

A 端是云端 Server（`118.89.196.44`），B 端是另一台机器 `vcptoolbox`（VM-0-13-ubuntu）。此前 A2A 只在单机做过，这一节补上真正的跨机链路。

准备：

1. 目标机 `dsh` 只有 `web` profile，按最小配置新建 `acp` profile（`package.json` 声明 `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-acp-app`，`cordis.yml` / `cordis.patch.yml` 为 `[]`）。
2. 登记 placement：`vcpdeck agents create --client=vcptoolbox --agent=dsh --adapter=acp --command=/usr/local/bin/dsh --arg=--profile --arg=acp --cwd=/var/lib/vcpdeck-client/home --workspace-root=...`。
3. 凭据：该机此前没有任何 LLM 凭据，首次派活 `task_89056714a98e47b8` 立即失败，Task.errorMessage 写明 `llm-deepseek: no API key for provider route "deepseek-official"`。把 `DEEPSEEK_API_KEY` 写入该机 `~vcpdeck/.dsh/.credentials.yaml` 的 `refs` 段（`600`，仅 `vcpdeck` 可读；临时密钥文件用后即删），未改动任何 systemd 服务。

结果（`task_02a186f570e14aea`）：`TASK_STATE_COMPLETED`，agent 返回 6 项配置。操作者用 VCPDeck jobs 在**同一台机器**独立复核，逐项一致：

| 项 | agent 汇报 | 独立复核 |
| --- | --- | --- |
| 主机 / 发行版 | VM-0-13-ubuntu / Ubuntu 22.04.4 LTS | 同 |
| 内核 | 5.15.0-113-generic | 同 |
| CPU | AMD EPYC 7K62，逻辑 4 核 | 同 |
| 内存 | 总量 3.3 GiB、可用约 848 MiB | 总量 3.3 GiB、可用 815 MiB（实时波动） |
| 根分区 | `/dev/vda2` 69G / 已用 43G / 剩 24G / 65% | 同 |
| GPU | 无 NVIDIA 设备，仅 Cirrus 虚拟显示 | `/dev/nvidia*` 0 个、无 `nvidia-smi` |

### 9.2 取消：状态正确，进程未回收（缺陷）

派发长任务 `task_147dfa54248242f2`（每 10 秒一轮、共 12 轮），12 秒后 `CancelTask`：

- 状态：`WORKING → CANCELED`，事件 `task.canceled` 正确写入；
- 但目标机上 `dsh --profile acp` 进程仍存活，且 agent 启动的 shell 循环
  （`for i in $(seq 1 12); do sleep 10; ...`）**继续执行**，直到手动 `kill`。

同一台机器上还积压了 5 个 `dsh --profile acp` 进程（`etime` 从 1h25 分到 33 秒），对应此前若干次已完成的任务——**完成态同样不回收**。

根因（读码确认）：

- 服务端 `TaskDispatchService.settle()` 收尾只做落库、清 pending、删 runtime，**从不向 Client 发 `close` 命令**；
- `cancel()` 只发 `cancel`（对应 ACP `session/cancel`），不发 `close`；
- Client 侧 `closeRuntime()`（内部 `session/close` + `process.kill()`）只在收到 `close` 命令或 **socket 断开**时触发。

影响：每个任务都会留下一个常驻 agent 进程；长任务被取消后其工具命令可能继续跑。本机（开发环境）未观察到同类残留，推测与开发客户端频繁重启（disconnect 会触发 closeRuntime）有关，不能据此认为 Windows 侧无此问题。

本次测试产生的 5 个进程与孤儿循环已手动终止。修复方向（未实施）：`settle()` 在终态一律补发 `close`，并让 `cancel()` 在 `session/cancel` 未收敛时升级为 `close`（进程级终止）。
