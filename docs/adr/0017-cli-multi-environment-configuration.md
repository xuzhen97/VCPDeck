# ADR-0017：CLI 使用用户级环境注册表与项目级默认环境选择器

- 状态：Accepted
- 日期：2026-08-18
- 决策者：项目维护者
- 关联：[`docs/design/cli.md`](../design/cli.md)、[`docs/security.md`](../security.md)、[`ADR-0009`](./0009-trusted-operator-security-domain.md)、[`ADR-0011`](./0011-server-side-opaque-authentication-and-actor-context.md)

## 背景

同一操作者可能在开发、测试、家庭网络和生产等多个环境部署 VCPDeck。CLI 后续会逐步对齐 Server 的机器、Job、文件、Terminal、Pi、FRP、Storage 和 Release 能力，如果每个命令单独接收 Server 与认证参数，容易产生重复实现、凭据泄漏和误操作目标环境的问题。

操作者还需要在某个项目或目录中设置默认环境，使 Pi Skill 和人工 CLI 调用优先使用项目上下文。但项目文件可能来自 Git 克隆或其他不完全可信来源；若允许项目直接定义 Server URL、Token 环境变量或明文凭据，进入目录后执行 CLI 可能把本机秘密发送到攻击者控制的 Server。

因此需要在 CLI 扩展更多业务命令前，固定环境配置的数据权威、查找优先级、凭据边界和项目配置权限。

## 决策

1. 用户级环境注册表固定为 `~/.vcpdeck/cli/config.json`，配置版本从 `1` 开始。它负责定义环境名、Server origin、认证类型、用户名和凭据环境变量名称。
2. 用户级配置不保存密码、Bearer Token、Cookie、PSK 或其他秘密明文。密码和 Token 只从已声明的环境变量读入进程内存。后续如引入系统凭据存储，需保持“配置只引用秘密、不内嵌秘密”的边界。
3. 项目级选择器固定名为 `.vcpdeck.json`，只允许 `{version, environment}`。它只能引用用户级已注册环境，不得定义 Server、认证类型、用户名、凭据变量名或秘密。
4. 环境选择优先级为：
   1. 命令显式 `--env` / `--environment`；
   2. `VCPDECK_ENVIRONMENT`；
   3. 从当前目录向上查找的最近 `.vcpdeck.json`；
   4. 用户级 `defaultEnvironment`；
   5. 无选择时明确失败。
5. 项目查找在发现最近选择器后停止；若处于 Git 仓库中，最多查到仓库根，不继承仓库外父目录选择器。`env use --local` 优先更新最近已有选择器，否则写到 Git 根；非 Git 目录写到当前目录。
6. 项目配置损坏、版本未知、含未知字段或引用不存在环境时 fail closed，不回退到全局默认。显式环境名和用户级配置也执行严格运行时校验。
7. `--server` 保留为现有脚本的临时直连兼容模式，优先于持久配置；它不能与 `--env` 同时使用。直连模式当前使用用户名/密码；命名环境支持 password 或 Bearer。
8. 所有未来业务命令都消费同一个已解析环境，不自行读取配置或复制认证选择逻辑。SDK 继续只接受明确 `baseUrl` 和 `auth`，不感知环境名、当前目录和配置文件。
9. CLI 和 Skill 在有副作用操作前展示最终环境名、Server 和配置来源；只展示凭据变量名，不展示其值。CLI 的同步成功不替代 Server/Job/Release 等业务终态核验。
10. 用户级配置使用临时文件 + rename 原子写入；非 Windows 下目录和文件权限分别收紧为 `0700`、`0600`。项目选择器允许提交 Git，但不得含秘密。
11. 环境名、Server URL、认证类型、凭据变量名和未知字段都进行严格校验；Server 必须是无用户名密码、query、fragment 和业务路径的 HTTP/HTTPS origin。
12. 新命名环境默认推荐 Frontend `/settings/tokens` 创建的 Bearer Credential；`env add --token-env=<VAR>` 可省略 `--auth=bearer`，仍落为既有 version 1 Bearer 结构。`env check` 通过 SDK `/api/auth/me` 验证凭据对应身份。Password 环境和显式 `--auth=bearer` 保持兼容，不迁移或重写用户配置。

## 候选方案

### 每个项目完整定义 Server 和认证

使用直观，但不可信仓库可以把 CLI 指向攻击者 Server，并诱导读取本机凭据变量；相同环境还会在多个项目重复配置，拒绝采用。

### 只使用环境变量，不建立注册表

适合单个 CI 任务，但多个环境的 Server、用户名和 Token 名称难以发现与复用，也无法安全表达项目默认环境，拒绝作为唯一方案。

### 把密码或 Token 加密保存在配置文件

没有外部密钥或系统凭据存储时，本地“加密”只是在同处保存解密能力，不能形成有效安全边界。本阶段只保存环境变量引用。

### 项目配置覆盖用户级任意字段

灵活但会让项目上下文改变认证和网络目标，扩大供应链风险；明确拒绝。

### SDK 直接管理环境配置

会让框架无关 REST 客户端依赖文件系统、HOME 和当前目录，破坏浏览器/Node 共用边界，拒绝采用。

## 后果

### 正面

- 多个部署环境有稳定、可发现且可复用的名称；
- 项目可提交一个不含秘密的默认环境选择器；
- 后续所有 CLI 命令共享同一目标与认证解析；
- Skill 可通过 `env current` 获取权威安全摘要，不复制配置规则；
- 错误项目配置不会静默回退并误操作全局默认环境。

### 负面

- 使用命名环境前必须先注册环境并设置对应凭据变量；
- 项目环境名需要每位操作者在本机注册同名环境；
- 环境变量仍可能被同账户进程读取，不等同于系统凭据保险箱；
- 项目文件虽然不含 URL/凭据，仍可选择已注册的高风险环境，因此写操作仍需显示目标和确认。

### 兼容与运维影响

- 现有 `release upload --server=...` 保持可用；`--server` 与 `--env` 混用改为明确拒绝；
- 命名环境成为后续 CLI 的推荐入口；
- 用户级配置应纳入本机配置备份但不得进入仓库；项目 `.vcpdeck.json` 可按团队需要提交；
- 环境删除会同时清除匹配的全局默认，但不会自动遍历删除项目选择器；引用被删环境的项目后续明确失败。

## 验证与退出条件

最低验证包括：严格 parser、未知字段/明文秘密拒绝、选择优先级、最近父目录与 Git 根、项目损坏/未知环境 fail closed、password/Bearer 凭据缺失、直连兼容与参数冲突、原子写入/POSIX 权限、Release 使用解析环境，以及 Skill 不绕过 CLI。

若需要团队共享完整环境定义、集中配置服务、系统钥匙串、云身份、自动环境发现或项目级 Server override，必须重新评估信任边界并用新 ADR 替代或扩展本决策，不能放宽 `.vcpdeck.json` 现有权限后静默演进。
