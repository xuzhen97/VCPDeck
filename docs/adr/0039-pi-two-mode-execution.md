# ADR-0039：Pi 两模式执行与逐工具策略移除

- 状态：Accepted
- 日期：2026-10-07
- 决策者：项目维护者
- 实施状态：尚未实现；Accepted 表示长期方向已确认，不表示当前运行行为已切换。
- 关联：[ADR-0034](./0034-pi-session-execution-mode-override.md)、[ADR-0033](./0033-pi-tool-approval-mode.md)、[ADR-0030](./0030-pi-resource-bundle-and-tool-policy.md)、[ADR-0007](./0007-client-owned-interactive-runtime.md)、[ADR-0008](./0008-pi-session-job-and-run-lifecycle.md)、[ADR-0036](./0036-pi-sdk-single-file-and-shell-capability.md)

## 背景

当前运行时叠加逐工具 `allow / confirm / deny` 分类与 `approval / auto / yolo` 模式。Auto 合并 allow 与 confirm 的执行行为，YOLO 则忽略三桶；操作者需要理解两套配置，受信扩展注册的新工具还需要额外进入策略配置。

VCPDeck 当前面向可信操作者的个人协作驾驶台。按工具名分类可以缩小模型工具集合，但无法区分同一 shell 工具中的查询与破坏性操作，也不能约束扩展代码直接访问系统。继续扩展逐工具权限目录增加配置与协议成本，不能提供等价的操作安全保证。

因此选择简化模型工具调用的监督方式，同时保持代码来源、会话控制和存量权限变化的显式边界。

## 决策

### 1. 删除逐工具三桶，仅保留两种执行模式

目标模式为 `supervised | automatic`：

- **supervised（监督）**：每次模型工具调用必须取得明确批准，包含读取工具；拒绝、取消或超时均不执行。
- **automatic（自动）**：模型直接调用当前运行时实际注册的工具，无逐次人工审批。

Profile、Session 覆盖与 Run 使用同一枚举；不复用旧枚举并偷偷改变含义。新建 Profile 的界面和 API 缺省统一为 supervised，automatic 必须显式选择。删除三桶，不引入隐式低风险豁免或自动风险分类。

可用能力由平台可用的内置工具与已启用受信扩展实际注册的工具组成；不再维护 Server 逐工具授权目录。未注册工具不可执行，未启用资源不得加载。执行模式或审批桥接缺失、未知或版本不兼容时拒绝执行，不猜默认值。

### 2. 保留会话覆盖与 Run 固化约束

本 ADR 替代 ADR-0034 继承的三桶策略、三种模式及旧枚举取值，不整体废弃 ADR-0034。

以下约束继续有效：Server 保存 Profile 默认与 Session 覆盖；未覆盖会话动态跟随已就绪 Profile；只有 Owner 在权威确认空闲时可修改覆盖；模式修改与 Run 接纳必须原子排序；每个 Run 固化有效模式；Client 工具装配与审批桥接同源；活跃 Run 不热切换，空闲 Worker 按 revision/模式安全换代；协议不兼容明确拒绝。

### 3. 存量受限配置不得静默扩大权限

- 旧 yolo Profile 映射为 automatic，其三桶原本不参与最终许可判定。
- 旧 approval/auto Profile 必须显式确认移除逐工具限制并选择新模式，确认前禁止新 Run，不根据桶内容猜测是否可安全自动迁移。
- 旧 Session yolo 覆盖映射为 automatic；旧 approval/auto 覆盖必须由 Owner 在空闲时选择新模式或清除覆盖，不能自动映射。
- Profile 未确认时，Session 覆盖不得绕过门控；Profile 确认也不得自动解除旧 Session 覆盖的待确认状态。
- 迁移保留旧限制用于一次性说明，但不得成为新运行时的第二套策略。确认经 Server 配置写权限校验并绑定 revision，拒绝过时确认。
- 历史只读访问保留，不为了读取历史启动可执行扩展。新建会话与其他会加载可执行扩展的操作同样受迁移门控。

升级前正常 drain 活跃 Run，备份数据库；迁移未完成给出可操作原因。不得将新语义误称为与旧受限配置行为等价。

### 4. 保持运行时与信任边界，显式升级协议

RuntimeSpec、Session/Run 模式协议、进程内 host bridge 与执行模式扩展资源必须显式版本化；Shared、Server、Client、SDK、Frontend 协同更新，Server-first 部署。旧 Client 不得忽略新字段或回退执行，新 Client 不得默默解释旧模式；回退需另行评估数据库与资源兼容。

执行模式继续经内存传递，不落入设置文件或通用子进程环境。扩展代码仍来自已校验的 Client Release Bundle，不因此增加包安装、项目或用户资源扫描。

监督仅覆盖 SDK 模型工具调用链，不覆盖扩展工厂、事件或命令处理器直接访问系统。启用扩展意味着信任其代码；两种模式均非 OS 沙箱，不改变 Client 账户权限、Provider/Model 策略、隔离数据根、Owner/Observer 或 Client 持有正文的边界。

## 候选方案

1. **只删除显式 deny，未列出即禁用**：保留了原有能力限制，但仍需要逐工具分桶，不能解决扩展配置负担。
2. **工具启用集合加统一审批模式**：概念比三桶清晰，但仍需维护工具目录与启用配置；当前阶段不保留这一层。
3. **保留三桶与三模式并扩展工具目录**：能力分类更精细，但配置复杂度持续增长；不符合此次简化目标。
4. **自动识别高风险工具或命令替代三桶**：需要额外风险模型与可验证规则，容易误判；不作为本次替代方案。

## 后果

正面：操作者只需选择监督程度；扩展工具随受信扩展启用自然进入运行时；内置与扩展工具采用统一执行语义；既有会话模式权威与并发约束保留。

成本与风险：失去逐工具禁用及“读取直行、写入审批”的配置能力；监督模式读取调用也会增加交互；自动模式将已注册能力交给模型直接调用，扩展来源与 OS 权限边界更重要。旧受限配置需人工确认，协议必须协同升级，不能无提示保持旧客户端可运行。

实施义务：同步 Current、安全、兼容、部署/迁移说明和 CHANGELOG；说明 Accepted 决策与实施状态，不将尚未实现的新语义写成现有能力。本 ADR 不确立扩展网页命令与 UI 的具体契约，该决策另行确认。

## 验证与退出条件

至少验证：

- 真实 SDK 中内置与扩展工具在 supervised 下均先审批，拒绝/取消/超时不执行，并行审批不串位；automatic 下已注册工具直接执行。
- 非法模式、桥接异常、未知工具与协议错位 fail closed，单文件发布布局保持扩展运行时导入能力。
- Profile 旧三模式与 Session 空覆盖/旧三模式的迁移组合均覆盖；待确认状态不被覆盖绕过，revision 冲突与 Observer 修改拒绝。
- SDK 工具集合与桥接使用同一 Run 模式，活跃 Run 不热切换；重连与换代不沿用旧配置。
- native Pi 零污染、正文不进 Server 持久层与日志、Client 平台 shell 能力及 Owner/Run 生命周期门禁继续通过。

若未来出现跨信任域、多租户、必须按工具限制能力、强制 Risk Guard 或 SDK 原生审批语义，应重新评估并由新 ADR 调整，不在两模式中暗加未经确认的策略层。
